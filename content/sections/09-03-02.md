Il passo finale dell'automazione: lo script parte **da solo** ogni mattina alle 7, elabora i file arrivati durante la notte, scrive il report e ti avvisa solo se qualcosa non va. Perché funzioni senza nessuno davanti, lo script deve rispettare alcune regole che quando lo lanci tu non contano.

```python
import json
from pathlib import Path

Path("arrivi").mkdir()
for nome in ["P01.csv", "P02.csv"]:
    (Path("arrivi") / nome).write_text("t;F\n")

def elabora_nuovi(cartella, registro=Path("elaborati.json")):
    fatti = set(json.loads(registro.read_text())) if registro.exists() else set()
    nuovi = [f for f in sorted(Path(cartella).glob("*.csv")) if f.name not in fatti]
    for f in nuovi:
        pass                                    # qui l'elaborazione vera
    registro.write_text(json.dumps(sorted(fatti | {f.name for f in nuovi})))
    return [f.name for f in nuovi]

print(elabora_nuovi("arrivi"))      # → ['P01.csv', 'P02.csv']
print(elabora_nuovi("arrivi"))      # → []
```

La seconda esecuzione non rifà il lavoro già fatto: lo script è **idempotente**, cioè lanciarlo due volte dà lo stesso risultato che lanciarlo una. È la proprietà più importante di uno script pianificato.

## Cosa cambia quando nessuno guarda

| Quando lo lanci tu | Quando parte da solo |
|---|---|
| la cartella corrente è quella del progetto | la cartella corrente può essere qualsiasi: usa percorsi assoluti |
| leggi gli errori sullo schermo | nessuno legge lo schermo: scrivi tutto in un **file di log** |
| se chiede qualcosa, rispondi | non c'è nessuno: niente `input()` |
| se si interrompe, lo rilanci | deve poter ripartire senza danni (idempotenza) |
| sai se è andato bene | lo deve dire lui: **codice di uscita** e, se serve, un avviso |

Per i percorsi, la cartella dello script si ricava da `__file__`, la variabile con il percorso del file `.py` in esecuzione:

```python norun
from pathlib import Path

BASE = Path(__file__).resolve().parent        # la cartella in cui sta lo script
DATI = BASE / "dati"
LOG = BASE / "log" / "collaudo.log"
```

## Idempotenza: ricordare cosa è già stato fatto

Il registro della scheda ricorda i **nomi** dei file. Se un file può essere corretto e rimandato con lo stesso nome, conviene ricordare anche il suo **contenuto**, con un'impronta (*hash*): una stringa calcolata dai byte del file, che cambia se cambia anche un solo carattere.

```python
import hashlib
from pathlib import Path

def impronta(file):
    return hashlib.sha256(Path(file).read_bytes()).hexdigest()

Path("P01.csv").write_text("t;F\n0;0\n1;12.5\n")
a = impronta("P01.csv")
Path("P01.csv").write_text("t;F\n0;0\n1;12.6\n")      # un solo carattere diverso
b = impronta("P01.csv")
print(len(a), a == b)                # → 64 False
print(a[:12])                        # → da8b52e5382e
```

SHA-256 produce sempre 64 caratteri esadecimali; due file diversi non danno mai, in pratica, la stessa impronta. Nel registro si salva allora `{nome: impronta}`, e un file si rielabora se è nuovo **o** se la sua impronta è cambiata.

Altre due regole di idempotenza:

- scrivi i risultati in un file **temporaneo** e rinominalo alla fine (`tmp.replace(finale)`): se lo script si interrompe a metà, il file vecchio resta intatto invece di trovarne uno mezzo scritto;
- aggiorna il registro **dopo** aver elaborato un file, non prima: se l'elaborazione fallisce, al giro successivo il file viene ripreso.

```python
from pathlib import Path

def scrivi_sicuro(file, testo):
    file = Path(file)
    tmp = file.with_suffix(file.suffix + ".tmp")
    tmp.write_text(testo)
    tmp.replace(file)              # sostituzione in un colpo solo

scrivi_sicuro("riepilogo.csv", "pezzo;esito\nA001;OK\n")
print(Path("riepilogo.csv").read_text().splitlines())    # → ['pezzo;esito', 'A001;OK']
print(Path("riepilogo.csv.tmp").exists())                # → False
```

## Il log su file

Il modulo `logging` (sezione 8.1.1) può scrivere su un file invece che sullo schermo. Ogni riga riporta data e ora, il livello e il messaggio: quando qualcosa va storto alle 3 di notte, il log è l'unico testimone.

```python
import logging
from pathlib import Path

log = logging.getLogger("collaudo")
log.setLevel(logging.INFO)
gestore = logging.FileHandler("collaudo.log", encoding="utf-8")
gestore.setFormatter(logging.Formatter("%(asctime)s %(levelname)-7s %(message)s", "%Y-%m-%d %H:%M:%S"))
log.addHandler(gestore)

log.info("avvio: 12 file da elaborare")
log.warning("P07.csv: 3 righe malformate scartate")
try:
    1 / 0
except ZeroDivisionError:
    log.exception("P09.csv: elaborazione fallita")       # scrive anche il traceback completo
gestore.close()

righe = Path("collaudo.log").read_text(encoding="utf-8").splitlines()
print(righe[1][20:])                  # → WARNING P07.csv: 3 righe malformate scartate
print(righe[-1])                      # → ZeroDivisionError: division by zero
```

- `log.exception` va usato dentro un `except`: aggiunge da solo il traceback;
- con `logging.handlers.RotatingFileHandler("collaudo.log", maxBytes=1_000_000, backupCount=5)` il file non cresce all'infinito: superato un megabyte si rinomina e se ne apre uno nuovo, tenendo gli ultimi cinque.

## Un lucchetto contro le sovrapposizioni

Se un'esecuzione dura più del previsto, la successiva può partire mentre la prima lavora ancora, e le due si pestano i piedi. Un **file di lock** lo impedisce: lo script lo crea all'avvio e lo cancella alla fine; se all'avvio esiste già, un'altra copia sta girando.

```python
from pathlib import Path

LOCK = Path("collaudo.lock")

def lavora():
    try:
        LOCK.touch(exist_ok=False)          # fallisce se il file esiste già
    except FileExistsError:
        return "un'altra esecuzione è in corso: esco"
    try:
        return "lavoro fatto"               # qui il lavoro vero
    finally:
        LOCK.unlink()                       # sempre, anche se il lavoro fallisce

print(lavora())                    # → lavoro fatto
LOCK.touch()                       # simuliamo un'esecuzione ancora in corso
print(lavora())                    # → un'altra esecuzione è in corso: esco
```

`finally` (Parte I) garantisce che il lucchetto venga tolto anche in caso di errore. Se il computer si spegne a metà, il lock resta: nel messaggio di errore indica il percorso del file, così chi legge il log sa cosa cancellare.

## Codice di uscita e struttura dello script

Il pianificatore guarda il **codice di uscita**: 0 vuol dire «tutto bene», qualunque altro numero «qualcosa è andato storto». Lo script pianificato ha questa forma:

```python norun
import logging
import sys

def main():
    configura_log()
    try:
        risultato = elabora_nuovi(DATI)
    except Exception:
        logging.getLogger("collaudo").exception("errore imprevisto")
        avvisa("Collaudo: errore imprevisto, vedi il log")
        return 2
    if risultato.scarti:
        avvisa(f"Collaudo: {len(risultato.scarti)} pezzi non conformi")
        return 1
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

## Pianificare su Windows

L'**Utilità di pianificazione** (*Task Scheduler*) lancia un programma a orari fissi. Dall'interfaccia: *Crea attività di base*, scegli orario e giorni, come programma metti il Python dell'ambiente virtuale e come argomento lo script.

Lo stesso con un comando, nel terminale:

```bash
schtasks /Create /TN "Collaudo mattutino" /SC WEEKLY /D MON,TUE,WED,THU,FRI /ST 07:00 ^
  /TR "C:\Progetti\collaudo\.venv\Scripts\python.exe C:\Progetti\collaudo\collaudo.py"
```

Usa sempre il `python.exe` **dentro** `.venv`: è quello con le librerie del progetto installate.

## Pianificare su macOS e Linux: cron

`cron` legge una tabella di righe, una per attività, che si modifica con `crontab -e`. Ogni riga ha cinque campi di orario e poi il comando:

```text
# minuto  ora  giorno-del-mese  mese  giorno-della-settimana   comando
  0       7    *                *     1-5                      /home/ing/collaudo/.venv/bin/python /home/ing/collaudo/collaudo.py >> /home/ing/collaudo/cron.log 2>&1
```

| Campo | Valori | Esempio |
|---|---|---|
| minuto | 0–59 | `0`, `*/15` (ogni 15 minuti) |
| ora | 0–23 | `7`, `8-18` |
| giorno del mese | 1–31 | `1` (il primo del mese) |
| mese | 1–12 | `*` (tutti) |
| giorno della settimana | 0–7 (0 e 7 = domenica) | `1-5` (lunedì–venerdì) |

`>> cron.log 2>&1` aggiunge in fondo a un file tutto quello che lo script stampa, errori compresi: senza, l'output andrebbe perso. Su macOS il sistema nativo è `launchd`, ma `cron` funziona ugualmente.

## Calcolare il prossimo avvio

A volte serve sapere quando partirà la prossima esecuzione (per scriverlo nel report, o in uno script che resta acceso e dorme fino all'ora giusta). È un buon esercizio con le date della sezione 9.1.3:

```python
from datetime import datetime, time, timedelta

def prossimo_avvio(adesso, ora, giorni_lavorativi=True):
    """Prossimo istante alle `ora` (oggi se non è ancora passata), saltando sabato e domenica se richiesto."""
    candidato = datetime.combine(adesso.date(), ora)
    if candidato <= adesso:
        candidato += timedelta(days=1)
    while giorni_lavorativi and candidato.weekday() >= 5:     # 5 = sabato, 6 = domenica
        candidato += timedelta(days=1)
    return candidato

print(prossimo_avvio(datetime(2026, 3, 12, 6, 30), time(7, 0)))    # → 2026-03-12 07:00:00
print(prossimo_avvio(datetime(2026, 3, 12, 9, 15), time(7, 0)))    # → 2026-03-13 07:00:00
print(prossimo_avvio(datetime(2026, 3, 13, 9, 15), time(7, 0)))    # → 2026-03-16 07:00:00
```

Il 13 marzo 2026 è un venerdì: dopo le 7 il prossimo giorno lavorativo è lunedì 16.

## Avvisare quando serve

Un'email si prepara con `email.message.EmailMessage` e si spedisce con `smtplib`. La preparazione funziona ovunque:

```python
from email.message import EmailMessage

msg = EmailMessage()
msg["Subject"] = "Collaudo 14/03: 2 pezzi non conformi"
msg["From"] = "banco-prova@azienda.it"
msg["To"] = "qualita@azienda.it"
msg.set_content("Pezzi non conformi: A017, A031.\nReport completo in allegato.")
msg.add_attachment(b"pezzo;esito\nA017;KO\n", maintype="text", subtype="csv", filename="scarti.csv")
print(msg["Subject"])                       # → Collaudo 14/03: 2 pezzi non conformi
print(msg.is_multipart())                   # → True
```

La spedizione, sul computer, passa dal server di posta aziendale:

```python norun
import os
import smtplib

with smtplib.SMTP("smtp.azienda.it", 587, timeout=30) as s:
    s.starttls()                                             # connessione cifrata
    s.login("banco-prova@azienda.it", os.environ["SMTP_PASSWORD"])
    s.send_message(msg)
```

> [!trappola] Le password non si scrivono mai nel codice né nei file che finiscono su Git: si leggono da una **variabile d'ambiente** (`os.environ["SMTP_PASSWORD"]`) impostata sul computer che esegue lo script, o da un file di configurazione escluso da Git (sezione 9.4.2).

> [!ing] Un buon script pianificato è **silenzioso quando va tutto bene** e rumoroso quando no. Se ogni mattina arriva un'email «tutto ok», dopo una settimana nessuno le legge più, e l'email di errore passa inosservata.

## Riepilogo

- Uno script pianificato usa percorsi assoluti (`Path(__file__).resolve().parent`), non chiede input, scrive un log.
- Idempotenza: registro dei file fatti (nomi o impronte SHA-256), scrittura su file temporaneo e `replace`.
- `logging.FileHandler` (o `RotatingFileHandler`) e `log.exception` dentro gli `except`.
- Un file di lock evita esecuzioni sovrapposte; `finally` lo toglie sempre.
- Codice di uscita: 0 tutto bene, altro numero errore; Windows con l'Utilità di pianificazione, macOS e Linux con `cron`.
- `EmailMessage` per gli avvisi, password nelle variabili d'ambiente; avvisa solo quando serve.
