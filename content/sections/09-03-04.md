Mille prove in mille file CSV sono difficili da interrogare: «la media di Rm per materiale, solo dei provini di marzo, esclusi quelli con l'estensimetro difettoso» richiede di riaprirli tutti. Un **database** tiene tutto in un posto solo e risponde a domande come questa con una riga di **SQL**. SQLite è un database intero dentro un solo file, ed è già incluso in Python.

```python
import sqlite3

con = sqlite3.connect(":memory:")            # un database in memoria; su disco: "prove.db"
con.execute("CREATE TABLE prove (provino TEXT, materiale TEXT, Rm REAL)")
con.executemany("INSERT INTO prove VALUES (?, ?, ?)",
                [("P1", "S355", 512.0), ("P2", "S355", 498.5), ("P3", "S235", 402.1)])
for riga in con.execute("SELECT materiale, AVG(Rm) FROM prove GROUP BY materiale ORDER BY materiale"):
    print(riga)
```

Uscita:

```text
('S235', 402.1)
('S355', 505.25)
```

`CREATE TABLE` definisce una tabella con le sue colonne, `INSERT` aggiunge righe, `SELECT` interroga. Ogni risultato è una **tupla**.

## Tabelle, righe, colonne

Un database relazionale è un insieme di **tabelle**, come i fogli di un Excel molto disciplinato: ogni colonna ha un nome e un tipo, ogni riga è un record. SQLite ha pochi tipi:

| Tipo SQL | In Python | Esempio |
|---|---|---|
| `INTEGER` | `int` | numero del provino, conteggi |
| `REAL` | `float` | Rm, diametro misurato |
| `TEXT` | `str` | materiale, operatore, date in formato ISO |
| `NULL` | `None` | valore mancante |

E alcuni **vincoli** che il database fa rispettare da solo:

- `PRIMARY KEY`: identifica in modo univoco ogni riga (spesso un `INTEGER` che SQLite numera da sé);
- `NOT NULL`: il valore è obbligatorio;
- `UNIQUE`: niente doppioni (per esempio lo stesso file importato due volte);
- `CHECK (...)`: una condizione da rispettare, come `Rm > 0`.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("""
    CREATE TABLE prove (
        id        INTEGER PRIMARY KEY,
        provino   TEXT    NOT NULL UNIQUE,
        materiale TEXT    NOT NULL,
        data      TEXT    NOT NULL,           -- AAAA-MM-GG
        Rm        REAL    CHECK (Rm > 0),
        note      TEXT
    )
""")
con.execute("INSERT INTO prove (provino, materiale, data, Rm) VALUES ('P01', 'S355', '2026-03-14', 512.0)")
try:
    con.execute("INSERT INTO prove (provino, materiale, data, Rm) VALUES ('P01', 'S355', '2026-03-14', 515.0)")
except sqlite3.IntegrityError as e:
    print(e)                       # → UNIQUE constraint failed: prove.provino
try:
    con.execute("INSERT INTO prove (provino, materiale, data, Rm) VALUES ('P02', 'S355', '2026-03-14', -3)")
except sqlite3.IntegrityError as e:
    print(e)                       # → CHECK constraint failed: Rm > 0
print(con.execute("SELECT id, provino, note FROM prove").fetchall())   # → [(1, 'P01', None)]
```

In SQL i commenti iniziano con `--`. I vincoli sono una rete di sicurezza: un dato sbagliato viene rifiutato **quando entra**, non scoperto mesi dopo in un grafico strano.

Quando importi più volte la stessa cartella vuoi **saltare** i provini già presenti invece di fermarti: `INSERT OR IGNORE` fa proprio questo. Attenzione però: ignora in silenzio **qualunque** violazione, anche quella del `CHECK`. I controlli sui valori, in quel caso, falli in Python prima di inserire.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE prove (provino TEXT PRIMARY KEY, Rm REAL CHECK (Rm > 0))")
cur = con.executemany("INSERT OR IGNORE INTO prove VALUES (?, ?)", [("P01", 512.0), ("P01", 515.0), ("P02", -3.0)])
print(cur.rowcount, con.execute("SELECT * FROM prove").fetchall())   # → 1 [('P01', 512.0)]
```

Il doppione di P01 e il valore negativo di P02 sono spariti entrambi senza errori: comodo per il primo, pericoloso per il secondo.

## SQL in sei istruzioni

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE prove (provino TEXT, materiale TEXT, data TEXT, Rm REAL, A REAL)")
con.executemany("INSERT INTO prove VALUES (?, ?, ?, ?, ?)", [
    ("P01", "S355", "2026-03-02", 512.0, 24.1), ("P02", "S355", "2026-03-02", 498.5, 22.8),
    ("P03", "S235", "2026-03-09", 402.1, 28.4), ("P04", "S235", "2026-03-09", 395.7, 29.0),
    ("P05", "S355", "2026-03-16", 521.3, 23.5), ("P06", "C45",  "2026-03-16", 688.0, 16.2),
])

q = lambda sql: con.execute(sql).fetchall()

print(q("SELECT provino, Rm FROM prove WHERE materiale = 'S355' AND Rm > 500"))
print(q("SELECT provino FROM prove ORDER BY Rm DESC LIMIT 2"))          # → [('P06',), ('P05',)]
print(q("SELECT COUNT(*), MIN(Rm), MAX(Rm) FROM prove WHERE data >= '2026-03-09'"))   # → [(4, 395.7, 688.0)]
print(q("SELECT materiale, COUNT(*), ROUND(AVG(A), 1) FROM prove GROUP BY materiale HAVING COUNT(*) >= 2"))
```

Uscita:

```text
[('P01', 512.0), ('P05', 521.3)]
[('P06',), ('P05',)]
[(4, 395.7, 688.0)]
[('S235', 2, 28.7), ('S355', 3, 23.5)]
```

| Istruzione | Cosa fa |
|---|---|
| `SELECT colonne FROM tabella` | sceglie le colonne (`*` per tutte) |
| `WHERE condizione` | filtra le righe (`=`, `<>`, `<`, `AND`, `OR`, `IN (...)`, `LIKE 'S%'`, `IS NULL`) |
| `ORDER BY colonna DESC` | ordina (`ASC` crescente, il default) |
| `LIMIT n` | prende solo le prime n righe |
| `GROUP BY colonna` | raggruppa e calcola `COUNT`, `AVG`, `MIN`, `MAX`, `SUM` per gruppo |
| `HAVING condizione` | filtra i **gruppi** (dopo `GROUP BY`), come `WHERE` filtra le righe |

Le date in formato ISO (`'2026-03-09'`) si confrontano come testo nel modo giusto: è il motivo pratico per cui conviene salvarle così (sezione 9.1.3). Per modificare e cancellare:

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE prove (provino TEXT, Rm REAL, note TEXT)")
con.executemany("INSERT INTO prove VALUES (?, ?, NULL)", [("P01", 512.0), ("P02", 12.0), ("P03", 498.5)])

cur = con.execute("UPDATE prove SET note = 'estensimetro scollegato' WHERE provino = 'P02'")
print(cur.rowcount)                                                   # → 1
con.execute("DELETE FROM prove WHERE note IS NOT NULL")
print(con.execute("SELECT provino FROM prove").fetchall())            # → [('P01',), ('P03',)]
```

> [!trappola] `UPDATE` e `DELETE` senza `WHERE` agiscono su **tutte** le righe. Prima di lanciarli, scrivi la stessa condizione in una `SELECT` e guarda quali righe tocca.

## I valori si passano con ?, mai con le f-string

È la regola più importante. I valori che arrivano da file, utenti o altri programmi si inseriscono con i **segnaposto** `?` (o `:nome`), e sqlite3 li passa al database separati dal comando.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE prove (provino TEXT, materiale TEXT)")
con.executemany("INSERT INTO prove VALUES (?, ?)", [("P01", "S355"), ("P02", "S235")])

materiale = "S355' OR '1'='1"                     # testo «malizioso» letto da un file
pericoloso = f"SELECT provino FROM prove WHERE materiale = '{materiale}'"
print(con.execute(pericoloso).fetchall())         # → [('P01',), ('P02',)]
sicuro = "SELECT provino FROM prove WHERE materiale = ?"
print(con.execute(sicuro, (materiale,)).fetchall())   # → []

print(con.execute("SELECT provino FROM prove WHERE materiale = :m", {"m": "S235"}).fetchall())   # → [('P02',)]
```

Con la f-string il testo è diventato parte del **comando** e ha cambiato la condizione: restituisce tutte le righe (si chiama *SQL injection*). Con `?` il testo resta un **valore** e non corrisponde a niente. Anche senza malizia, un apostrofo in un nome (`D'Amico`) rompe la f-string; il segnaposto no. Nota la virgola in `(materiale,)`: i parametri vanno sempre in una tupla, anche quando è uno solo.

## Transazioni: tutto o niente

Le modifiche diventano definitive solo con un **commit**. Il modo più sicuro è usare la connessione con `with`: se il blocco finisce bene salva tutto, se c'è un'eccezione annulla tutto (*rollback*). Così un'importazione interrotta a metà non lascia il database con metà dei dati.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE prove (provino TEXT UNIQUE, Rm REAL)")

lotto = [("P01", 512.0), ("P02", 498.5), ("P01", 515.0)]      # il terzo è un doppione
try:
    with con:
        con.executemany("INSERT INTO prove VALUES (?, ?)", lotto)
except sqlite3.IntegrityError as e:
    print("importazione annullata:", e)
print(con.execute("SELECT COUNT(*) FROM prove").fetchone()[0])     # → 0
```

Nessuna delle tre righe è entrata: o il lotto entra intero, o non entra. `fetchone()` restituisce la prima riga del risultato, `[0]` il suo primo valore.

## Due tabelle e JOIN

Ripetere «S355, fy nominale 355, Rm minimo 470» su ogni prova è uno spreco e una fonte di errori. Si mettono i materiali in una tabella a parte e ogni prova **rimanda** al suo materiale con una *chiave esterna*. `JOIN` riunisce le due tabelle nella risposta.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("PRAGMA foreign_keys = ON")              # SQLite controlla i rimandi solo se lo chiedi
con.executescript("""
    CREATE TABLE materiali (nome TEXT PRIMARY KEY, Rm_min REAL NOT NULL);
    CREATE TABLE prove (
        provino TEXT PRIMARY KEY,
        materiale TEXT NOT NULL REFERENCES materiali(nome),
        Rm REAL NOT NULL
    );
    INSERT INTO materiali VALUES ('S235', 360), ('S355', 470);
    INSERT INTO prove VALUES ('P01', 'S355', 512.0), ('P02', 'S355', 463.0), ('P03', 'S235', 402.1);
""")

sql = """
    SELECT p.provino, p.materiale, p.Rm, m.Rm_min, p.Rm >= m.Rm_min AS conforme
    FROM prove AS p JOIN materiali AS m ON p.materiale = m.nome
    ORDER BY p.provino
"""
for riga in con.execute(sql):
    print(riga)
try:
    con.execute("INSERT INTO prove VALUES ('P04', 'S460', 560.0)")
except sqlite3.IntegrityError as e:
    print(e)                                         # → FOREIGN KEY constraint failed
```

Uscita:

```text
('P01', 'S355', 512.0, 470.0, 1)
('P02', 'S355', 463.0, 470.0, 0)
('P03', 'S235', 402.1, 360.0, 1)
FOREIGN KEY constraint failed
```

- `executescript` esegue più istruzioni separate da `;` (senza parametri: solo per creare la struttura);
- `AS p` dà un nome breve alla tabella; `p.Rm >= m.Rm_min AS conforme` calcola una colonna nuova (SQLite scrive i booleani come 1 e 0);
- con le chiavi esterne attive, una prova su un materiale che non esiste viene rifiutata.

## Righe con i nomi delle colonne

Le tuple sono comode ma `riga[3]` non dice niente. Con `row_factory = sqlite3.Row` ogni riga si legge anche per nome, come un dizionario.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.row_factory = sqlite3.Row
con.execute("CREATE TABLE prove (provino TEXT, Rm REAL, A REAL)")
con.execute("INSERT INTO prove VALUES ('P01', 512.0, 24.1)")
r = con.execute("SELECT * FROM prove").fetchone()
print(r["provino"], r["Rm"], r.keys())          # → P01 512.0 ['provino', 'Rm', 'A']
print(dict(r))                                  # → {'provino': 'P01', 'Rm': 512.0, 'A': 24.1}
```

## SQLite e pandas

pandas legge il risultato di una query direttamente in un DataFrame, e scrive un DataFrame in una tabella: le due cose insieme fanno di SQLite l'archivio e di pandas lo strumento di analisi.

```python
import sqlite3
import pandas as pd

con = sqlite3.connect(":memory:")
df = pd.DataFrame({"provino": ["P01", "P02", "P03"], "materiale": ["S355", "S355", "S235"], "Rm": [512.0, 498.5, 402.1]})
df.to_sql("prove", con, index=False)                         # crea la tabella e inserisce le righe

media = pd.read_sql_query("SELECT materiale, AVG(Rm) AS Rm_medio FROM prove GROUP BY materiale", con)
print(media.to_dict("records"))      # → [{'materiale': 'S235', 'Rm_medio': 402.1}, {'materiale': 'S355', 'Rm_medio': 505.25}]
s355 = pd.read_sql_query("SELECT * FROM prove WHERE materiale = ?", con, params=("S355",))
print(len(s355))                     # → 2
```

`to_sql(..., if_exists="append")` aggiunge righe a una tabella esistente invece di crearla.

Per guardare dentro il file senza scrivere codice c'è **DB Browser for SQLite**, gratuito: mostra le tabelle come fogli di calcolo e permette di provare le query.

> [!nota] SQLite è perfetto per un laboratorio, un banco prova, un progetto di tesi: un file, nessun server, migliaia di righe al secondo. Quando molti utenti devono scrivere insieme da computer diversi si passa a un database con server (PostgreSQL), ma l'SQL che hai imparato resta quasi identico.

> [!ing] Progetta le tabelle pensando alle **domande** che farai: se chiederai «tutte le prove di un operatore» serve la colonna `operatore`; se chiederai «le prove di quella colata» serve il numero di colata. Una colonna aggiunta dopo vale solo per i dati nuovi.

## Riepilogo

- SQLite: un database in un file (`sqlite3.connect("prove.db")`), già incluso in Python.
- `CREATE TABLE` con tipi (`INTEGER`, `REAL`, `TEXT`) e vincoli (`PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `CHECK`).
- `SELECT … WHERE … ORDER BY … LIMIT`, `GROUP BY … HAVING` con `COUNT`, `AVG`, `MIN`, `MAX`; `UPDATE` e `DELETE` sempre con `WHERE`.
- Valori sempre con `?` o `:nome`, mai con le f-string.
- `with con:` per transazioni tutto-o-niente; `JOIN` per collegare tabelle, `PRAGMA foreign_keys = ON`.
- `sqlite3.Row` per leggere per nome; `pd.read_sql_query` e `df.to_sql` per lavorare con pandas.
