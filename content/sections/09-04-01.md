Uno script di 50 righe sta bene in un file. Quando arriva a 800 righe, lo usano tre colleghi e servono cinque comandi diversi, un file solo diventa un groviglio. Un **progetto** organizzato divide il codice in moduli con compiti chiari, ha i test accanto, si installa con un comando e si lancia con un nome.

```text
banco-prova/
├── pyproject.toml          ← nome, versione, dipendenze, comandi
├── README.md               ← cosa fa e come si usa
├── src/
│   └── banco/              ← il pacchetto: si importa con «import banco»
│       ├── __init__.py
│       ├── lettura.py      ← leggere i file del banco
│       ├── analisi.py      ← i calcoli (funzioni pure)
│       ├── report.py       ← Excel, Word, PDF
│       └── cli.py          ← la riga di comando: argparse, log, codici di uscita
└── tests/
    ├── test_lettura.py
    └── test_analisi.py
```

Ogni file ha **un** compito. I calcoli non sanno da dove arrivano i dati né dove finiscono: per questo si provano facilmente.

## Moduli e pacchetti, ripresi

Dalla Parte I sai che un file `.py` è un **modulo** e si importa con il suo nome. Una cartella con un file `__init__.py` è un **pacchetto**: un insieme di moduli che si importano con il punto.

```python norun
# dentro src/banco/cli.py
from banco.lettura import leggi_cartella
from banco.analisi import statistiche
from banco.report import scrivi_excel
```

`__init__.py` può essere vuoto; spesso contiene solo la versione (`__version__ = "1.2.0"`) o importa le funzioni principali, così chi usa il pacchetto può scrivere `from banco import leggi_cartella`.

Perché la cartella `src/`? Perché obbliga a **installare** il pacchetto prima di usarlo: i test girano allora sul codice installato, esattamente come lo userà un collega, e non per caso sui file che si trovano nella cartella corrente.

## Separare calcolo, dati e interfaccia

La regola che rende un progetto mantenibile: **le funzioni di calcolo non leggono file, non stampano e non chiedono niente**. Ricevono dati, restituiscono risultati. La lettura sta in un modulo, la scrittura in un altro, e la riga di comando li collega.

Un esempio in piccolo, tutto in un blocco: prima la versione «tutto insieme», poi la stessa divisa in tre.

```python
from pathlib import Path

Path("P01.csv").write_text("F;A\n48200;78.5\n")

# tutto insieme: difficile da provare, impossibile da riusare
def verifica_provino(file):
    righe = Path(file).read_text().splitlines()[1:]
    F, A = map(float, righe[0].split(";"))
    Rm = F / A
    print(f"{file}: Rm = {Rm:.0f} MPa, {'OK' if Rm >= 470 else 'KO'}")

verifica_provino("P01.csv")

# diviso: lettura, calcolo, presentazione
def leggi(file):                                   # lettura.py
    F, A = map(float, Path(file).read_text().splitlines()[1].split(";"))
    return F, A

def resistenza(F, A, Rm_min):                      # analisi.py: pura, si prova con due numeri
    Rm = F / A
    return Rm, Rm >= Rm_min

def riga_report(nome, Rm, ok):                     # report.py
    return f"{nome}: Rm = {Rm:.0f} MPa, {'OK' if ok else 'KO'}"

print(riga_report("P01.csv", *resistenza(*leggi("P01.csv"), Rm_min=470)))
assert resistenza(1000, 2, 470) == (500.0, True)  # il test non ha bisogno di nessun file
```

Le due versioni stampano la stessa riga; ma solo la seconda permette di provare il calcolo senza file, di cambiare formato del report senza toccare il calcolo, di leggere un formato nuovo senza toccare nient'altro.

## pyproject.toml

È il file che descrive il progetto: lo leggono pip, uv e gli editor. Ecco un esempio completo, letto con `tomllib` per mostrare che è un normale file di dati (sezione 9.1.3):

```python
import tomllib

PYPROJECT = '''
[project]
name = "banco-prova"
version = "1.2.0"
description = "Acquisizione, analisi e report delle prove di trazione"
requires-python = ">=3.11"
dependencies = [
    "pandas>=2.2",
    "openpyxl>=3.1",
    "python-docx>=1.1",
]

[project.optional-dependencies]
dev = ["pytest>=8", "ruff"]

[project.scripts]
banco = "banco.cli:main"

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
'''

p = tomllib.loads(PYPROJECT)["project"]
print(p["name"], p["version"])                 # → banco-prova 1.2.0
print([d.split(">")[0] for d in p["dependencies"]])   # → ['pandas', 'openpyxl', 'python-docx']
print(p["scripts"]["banco"])                   # → banco.cli:main
```

- `dependencies`: le librerie che servono, con la versione minima; chi installa il progetto le riceve in automatico;
- `optional-dependencies`: gruppi facoltativi, come gli strumenti per lo sviluppo (`pip install -e ".[dev]"`);
- `[project.scripts]`: `banco = "banco.cli:main"` crea un **comando** `banco` che chiama la funzione `main` del modulo `banco/cli.py`;
- `[build-system]`: lo strumento che impacchetta il progetto; `hatchling` è una scelta semplice e diffusa.

Con l'ambiente virtuale attivo, nella cartella del progetto:

```bash
pip install -e ".[dev]"     # -e: «modificabile», le modifiche al codice valgono subito
banco --help                # il comando ora esiste
pytest -q                   # i test girano sul pacchetto installato
```

Con **uv** lo stesso progetto si crea con `uv init --package banco-prova`, le dipendenze si aggiungono con `uv add pandas`, e `uv run banco` lancia il comando nell'ambiente giusto senza attivarlo. uv scrive anche un file `uv.lock` con le versioni **esatte** di tutto: chi lo usa ottiene un ambiente identico al tuo.

## La riga di comando con sottocomandi

Un progetto vero fa più cose: importare, analizzare, fare il report. argparse (sezione 8.1.1) gestisce i **sottocomandi** come fa `git` (`git add`, `git commit`):

```python
import argparse

def crea_parser():
    p = argparse.ArgumentParser(prog="banco", description="Strumenti del banco prova")
    p.add_argument("-v", "--verbose", action="store_true", help="messaggi dettagliati")
    sotto = p.add_subparsers(dest="comando", required=True)

    imp = sotto.add_parser("importa", help="importa i file del banco nel database")
    imp.add_argument("cartella")

    rep = sotto.add_parser("report", help="crea il report di un lotto")
    rep.add_argument("lotto")
    rep.add_argument("--formato", choices=["xlsx", "docx", "pdf"], default="xlsx")
    return p

a = crea_parser().parse_args(["report", "2026-118", "--formato", "pdf"])
print(a.comando, a.lotto, a.formato, a.verbose)        # → report 2026-118 pdf False
a = crea_parser().parse_args(["-v", "importa", "arrivi/"])
print(a.comando, a.cartella, a.verbose)                # → importa arrivi/ True
```

Nella funzione `main` un `match` (Parte II) sceglie cosa fare in base ad `a.comando`.

## Il logging in un pacchetto

Ogni modulo crea il **suo** logger con `logging.getLogger(__name__)`: `__name__` vale `"banco.analisi"`, `"banco.lettura"`…, così nei messaggi si vede da dove arrivano. I moduli **non configurano** niente: dove scrivere e con quale dettaglio lo decide solo `cli.py`, una volta, all'avvio.

```python
import io
import logging

# in banco/analisi.py
log_analisi = logging.getLogger("banco.analisi")      # nel file vero: logging.getLogger(__name__)
def media(valori):
    if not valori:
        log_analisi.warning("nessun valore: media non calcolabile")
        return None
    log_analisi.debug("media di %d valori", len(valori))
    return sum(valori) / len(valori)

# in banco/cli.py, all'avvio
def configura_log(verbose, flusso):
    gestore = logging.StreamHandler(flusso)
    gestore.setFormatter(logging.Formatter("%(levelname)s %(name)s: %(message)s"))
    radice = logging.getLogger("banco")
    radice.handlers[:] = [gestore]
    radice.setLevel(logging.DEBUG if verbose else logging.INFO)

uscita = io.StringIO()
configura_log(verbose=False, flusso=uscita)
media([512.0, 498.5])
media([])
print(uscita.getvalue().strip())       # → WARNING banco.analisi: nessun valore: media non calcolabile
```

Il messaggio di `debug` non compare perché il livello è `INFO`: con `--verbose` comparirebbe. `"media di %d valori", len(valori)` è la forma consigliata per i log: il testo si compone solo se il messaggio viene davvero scritto.

## Errori che parlano la lingua del progetto

Il pacchetto definisce le **sue** eccezioni, figlie di quelle standard: la riga di comando le riconosce e le trasforma in un messaggio chiaro e in un codice di uscita, mentre un errore imprevisto mostra il traceback completo (è un bug da correggere).

```python
class ErroreBanco(Exception):
    """Errore previsto: dati o configurazione sbagliati."""

class FileMalformato(ErroreBanco):
    def __init__(self, file, riga, motivo):
        super().__init__(f"{file}, riga {riga}: {motivo}")

def leggi_forza(file, testo):
    for n, riga in enumerate(testo.splitlines(), start=1):
        if n > 1 and len(riga.split(";")) != 2:
            raise FileMalformato(file, n, "attese 2 colonne")
    return "ok"

def main(argv):
    try:
        leggi_forza(*argv)
    except ErroreBanco as e:
        print("errore:", e)
        return 2
    return 0

print(main(["P01.csv", "F;A\n48200;78.5\n"]))          # → 0
print(main(["P02.csv", "F;A\n48200;78.5;x\n"]))
```

Uscita dell'ultima riga:

```text
errore: P02.csv, riga 2: attese 2 colonne
2
```

## Gli strumenti della qualità

| Strumento | Cosa fa | Comando |
|---|---|---|
| **pytest** | lancia i test (Parte II) | `pytest -q` |
| **ruff** | trova errori ed esempi di cattivo stile, e formatta il codice | `ruff check .` e `ruff format .` |
| **mypy** | controlla i type hint (Parte II) | `mypy src` |
| **pytest-cov** | misura quale parte del codice è coperta dai test | `pytest --cov=banco` |

Si configurano tutti in `pyproject.toml`, nella sezione `[tool.nome]`, così le regole sono le stesse per chiunque lavori al progetto. VS Code li usa da soli se installi le estensioni corrispondenti.

## README e versioni

Il **README** è la prima cosa che legge un collega: cosa fa il programma, come si installa, un esempio d'uso, dove sono i dati di prova. Cinque minuti di README risparmiano un'ora di spiegazioni.

La **versione** segue di solito lo schema *MAJOR.MINOR.PATCH* (`1.2.0`): si aumenta `PATCH` per una correzione, `MINOR` per una funzione nuova compatibile con prima, `MAJOR` quando cambia qualcosa che rompe l'uso di prima (un'opzione rinominata, un formato di file diverso). Scrivi la versione nei report generati: sapere quale versione ha prodotto un certificato è prezioso quando si scopre un bug.

## Distribuire ai colleghi

- **Dallo stesso repository Git** (sezione 9.4.2): `pip install git+https://github.com/azienda/banco-prova.git`; per aggiornare, lo stesso comando con `--upgrade`;
- **Come pacchetto**: `python -m build` crea un file `.whl` che si installa con `pip install banco_prova-1.2.0-py3-none-any.whl`;
- **Come eseguibile** per chi non ha Python: PyInstaller (`pyinstaller --onefile src/banco/cli.py`) crea un `.exe`. È comodo ma pesante (decine di MB) e va rifatto a ogni versione.

> [!ing] Il modo più rapido per migliorare un programma è farlo usare a un collega guardandolo **senza aiutarlo**: ogni volta che si blocca hai trovato un messaggio d'errore da chiarire, un default da cambiare o una riga di README da scrivere.

## Riepilogo

- Un pacchetto in `src/nome/` con moduli dai compiti chiari, `tests/` accanto, `pyproject.toml` e README.
- Le funzioni di calcolo sono pure: niente file, niente `print`, niente `input`; la CLI collega i pezzi.
- `pyproject.toml`: dipendenze, gruppi facoltativi, `[project.scripts]` per i comandi; `pip install -e ".[dev]"` o uv.
- Sottocomandi con `add_subparsers`; `logging.getLogger(__name__)` nei moduli, configurazione solo nella CLI.
- Eccezioni del progetto per gli errori previsti (messaggio e codice di uscita), traceback per i bug.
- pytest, ruff, mypy; versione *MAJOR.MINOR.PATCH* scritta nei report.
