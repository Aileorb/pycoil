«Ieri funzionava.» Con **Git** puoi vedere esattamente cosa è cambiato da ieri, tornare alla versione che funzionava, provare un'idea senza paura di rovinare quella buona e lavorare in tre sullo stesso progetto. È lo strumento che ogni programmatore usa ogni giorno, e anche questa app è costruita così.

```bash
cd banco-prova
git init                                   # da ora la cartella è un repository
git add .                                  # prepara tutti i file
git commit -m "Prima versione: lettura dei file del banco"
git log --oneline                          # la storia: un commit per riga
```

Un **commit** è una fotografia del progetto in un certo momento, con un messaggio che dice cosa è cambiato. La sequenza dei commit è la storia del codice, e ogni fotografia si può riaprire.

## Installare e presentarsi

Git si scarica da git-scm.com (su Windows lascia le opzioni predefinite; su macOS il primo `git` nel terminale propone di installarlo). Poi, una volta sola, dici chi sei: ogni commit porterà il tuo nome.

```bash
git --version
git config --global user.name "Mario Rossi"
git config --global user.email "mario.rossi@esempio.it"
git config --global init.defaultBranch main
```

## Le tre zone

Git tiene i file in tre posti, e capire il passaggio dall'uno all'altro è metà del lavoro:

```text
 cartella di lavoro  ──git add──▶  area di preparazione  ──git commit──▶  storia (repository)
 (i file che modifichi)            (cosa entrerà nel                      (le fotografie salvate)
                                    prossimo commit)
```

- modifichi i file come sempre, nell'editor;
- con `git add` scegli **quali** modifiche entrano nel prossimo commit (puoi fare un commit solo della correzione al calcolo, e uno a parte per il report);
- con `git commit` le salvi nella storia, per sempre.

## Il ciclo di ogni giorno

```bash
git status                    # cosa è cambiato? cosa è pronto per il commit?
git diff                      # le righe modificate, rispetto all'ultimo commit
git add src/banco/analisi.py  # prepara un file (o "git add ." per tutti)
git diff --staged             # cosa entrerà nel commit
git commit -m "Cpk: usa il limite più vicino alla media"
git log --oneline -5          # gli ultimi cinque commit
```

Un buon messaggio di commit dice **cosa** cambia e, se non è ovvio, **perché**, in una riga sotto i 70 caratteri: «Corregge Rm: l'area era in cm² invece che mm²» è utile tra sei mesi; «modifiche» o «fix» no.

Quando conviene fare un commit? Ogni volta che il codice è in uno stato **coerente** e i test passano: una funzione finita, un bug corretto. Meglio dieci commit piccoli che uno enorme a fine settimana: se qualcosa si rompe, trovi subito quale passo l'ha rotto.

`git status` ha una forma compatta pensata per i programmi, `--porcelain`: due lettere di stato e il nome del file. È un buon esercizio di lettura, e serve davvero se vuoi che uno script controlli di non avere modifiche non salvate prima di generare un report.

```python
STATO = """ M src/banco/analisi.py
M  src/banco/report.py
?? dati/prova_nuova.csv
 D vecchio.py"""

SIGNIFICATO = {"M": "modificato", "A": "aggiunto", "D": "cancellato", "?": "non tracciato"}
for riga in STATO.splitlines():
    preparato, lavoro, nome = riga[0], riga[1], riga[3:]
    if preparato == "?":
        print(f"{nome}: non tracciato")
    elif preparato != " ":
        print(f"{nome}: {SIGNIFICATO[preparato]}, pronto per il commit")
    else:
        print(f"{nome}: {SIGNIFICATO[lavoro]}, non ancora aggiunto")
```

Uscita:

```text
src/banco/analisi.py: modificato, non ancora aggiunto
src/banco/report.py: modificato, pronto per il commit
dati/prova_nuova.csv: non tracciato
vecchio.py: cancellato, non ancora aggiunto
```

La prima lettera è l'area di preparazione, la seconda la cartella di lavoro.

## .gitignore: cosa non va nella storia

Alcuni file non devono entrare mai: l'ambiente virtuale (si ricrea da `pyproject.toml`), i file che Python genera da solo, i risultati che il programma ricrea, e soprattutto **password e chiavi**. Si elencano in un file `.gitignore` nella cartella principale:

```text
# ambiente e file generati da Python
.venv/
__pycache__/
*.pyc
.pytest_cache/

# risultati che lo script ricrea
report/
*.xlsx
*.log

# dati grandi o riservati
dati/grezzi/
prove.db

# segreti: MAI su Git
.env
config_locale.toml
```

`*` vale «qualunque testo», come in `glob` (sezione 9.1.1); una riga che finisce con `/` indica una cartella. GitHub mantiene un modello completo per Python (nelle fonti).

> [!trappola] Una password finita in un commit resta nella storia anche se poi cancelli il file: chiunque abbia una copia del repository può recuperarla. Se succede, considerala **compromessa** e cambiala subito.

## Tornare indietro

| Situazione | Comando |
|---|---|
| annullare le modifiche a un file non ancora aggiunto | `git restore analisi.py` |
| togliere un file dall'area di preparazione | `git restore --staged analisi.py` |
| vedere com'era un file in un vecchio commit | `git show a1b2c3d:src/banco/analisi.py` |
| riprendere un file da un vecchio commit | `git restore --source a1b2c3d src/banco/analisi.py` |
| annullare un commit già fatto (con un nuovo commit «al contrario») | `git revert a1b2c3d` |
| trovare chi ha cambiato una riga e quando | `git blame src/banco/analisi.py` |

`a1b2c3d` è l'inizio dell'**hash** del commit, l'identificativo che vedi in `git log --oneline`. `git revert` è il modo sicuro di annullare: non cancella la storia, aggiunge un commit che fa il contrario.

```python
LOG = """e4f1a2c Report PDF: intestazione con numero di pagina
9b07d33 Cpk: usa il limite più vicino alla media
51c8e90 Lettura: accetta la virgola decimale
2a6f0b1 Prima versione: lettura dei file del banco"""

commit = [riga.split(" ", 1) for riga in LOG.splitlines()]
print(len(commit), "commit")                     # → 4 commit
print(commit[-1][0])                             # → 2a6f0b1
print([h for h, msg in commit if "Cpk" in msg])  # → ['9b07d33']
```

> [!trappola] Diffida dei comandi che riscrivono la storia, come `git reset --hard` e `git push --force`: cancellano lavoro in modo difficile da recuperare. Se un tutorial te li suggerisce per risolvere un problema, prima fai una copia della cartella.

## Rami: provare senza paura

Un **ramo** (*branch*) è una linea di sviluppo parallela. Vuoi provare un solutore diverso? Crei un ramo, lavori lì; il ramo `main` resta com'era. Se l'idea funziona la **unisci** (*merge*), altrimenti cancelli il ramo.

```bash
git switch -c prova-solutore-sparso     # crea il ramo e ci passa
# ... modifiche, commit, test ...
git switch main                         # torna alla versione principale
git merge prova-solutore-sparso         # porta in main le modifiche del ramo
git branch -d prova-solutore-sparso     # cancella il ramo, ormai unito
```

Se nel frattempo la stessa riga è stata cambiata in modo diverso nei due rami, Git non sa quale tenere e segnala un **conflitto**. Nel file trovi le due versioni marcate:

```text
<<<<<<< HEAD
gamma_M0 = 1.05
=======
gamma_M0 = 1.10
>>>>>>> prova-solutore-sparso
```

Si sceglie a mano la versione giusta (o una combinazione), si cancellano le righe con i segni `<<<<<<<`, `=======`, `>>>>>>>`, poi `git add` e `git commit`. VS Code mostra i conflitti con i pulsanti *Accept Current* / *Accept Incoming*.

## GitHub: una copia in rete

**GitHub** (o GitLab, o il server aziendale) tiene una copia del repository in rete: è il backup, il modo di lavorare in gruppo e il posto da cui i colleghi installano il programma.

```bash
git remote add origin https://github.com/mario-rossi/banco-prova.git   # una volta sola
git push -u origin main         # manda i tuoi commit
git pull                        # prendi i commit degli altri
git clone https://github.com/mario-rossi/banco-prova.git   # copia completa su un altro computer
```

In gruppo si lavora di solito così: ognuno crea un ramo per la sua modifica, lo manda su GitHub e apre una **pull request**, una richiesta di unire il ramo in `main`; un collega legge le modifiche, commenta, e solo dopo l'approvazione si unisce. È la revisione del codice, ed è il modo più efficace per imparare.

I repository possono essere **privati**: per il codice aziendale o della tesi è la scelta normale.

## Test automatici a ogni push

GitHub Actions può lanciare i test a ogni `push`, su un computer pulito: se qualcuno rompe qualcosa, lo sai subito. Basta un file `.github/workflows/test.yml`:

```text
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -e ".[dev]"
      - run: ruff check .
      - run: pytest -q
```

È esattamente come funziona questa app: ogni modifica ai contenuti fa partire un controllo che esegue tutti gli esempi e gli esercizi, e la pubblicazione avviene solo se è tutto verde.

## Git e i file che non sono codice

Git è pensato per il **testo**: per i file `.py`, `.toml`, `.md`, `.csv` piccoli mostra esattamente le righe cambiate. Con i file binari grandi (modelli CAD, video, database, Excel pesanti) non mostra le differenze e la storia si gonfia: tienili fuori con `.gitignore`, oppure usa **Git LFS** per i file grandi che devono stare nel repository. I notebook Jupyter salvano anche i risultati e le immagini: con `nbstripout` Git ne vede solo il codice.

> [!ing] Anche senza programmare, Git è utile per qualunque insieme di file di testo che evolve: specifiche, script di calcolo, file di input di un solutore, la tesi scritta in LaTeX o Markdown. Poter rispondere «cosa è cambiato tra la revisione B e la C» con un comando è prezioso.

## Riepilogo

- Un commit è una fotografia del progetto con un messaggio; `git init`, `git add`, `git commit`, `git log --oneline`.
- Tre zone: cartella di lavoro → area di preparazione (`add`) → storia (`commit`); `git status` e `git diff` per controllare.
- `.gitignore` per `.venv/`, `__pycache__/`, risultati rigenerabili e segreti; una password in un commit è compromessa.
- `git restore`, `git show`, `git revert` per tornare indietro senza riscrivere la storia.
- Rami per provare (`switch -c`, `merge`), conflitti risolti a mano; GitHub per backup, gruppo e pull request.
- GitHub Actions lancia i test a ogni push.
